为什么不能直接拿云端 agent 跑本地模型

现有 harness 的每一条默认假设，在一台自己的机器上都不成立。

云端假设

上下文没满就继续塞。窗口大小是唯一的约束。

本地现实

上下文没满，机器已经要 swap 了。内存压力必须和 token 占用一起参与压缩决策。

云端假设

需要并行就起子 agent，能起多少起多少。

本地现实

主 agent 正在 decode，子 agent 的 prefill 插进来抢 GPU，两边一起变慢。起之前得先问问机器答不答应。

云端假设

模型足够聪明，提示词里说清楚边界它就不会越界。

本地现实

参数量小一个量级，误操作概率高一个量级。隔离必须是系统级强制的，不能靠提示词约束。

云端假设

系统提示词写详细点，反正窗口够大。

本地现实

标称 128K，有效上下文远小于此。提示词每多一千 token，可用工作区就少一千。

三个设计决定

判断标准只有一条：如果一个决定对云端大模型和本地小模型的意义是一样的，那它就不是这个项目的重点，抄现成方案即可。

压缩看两个信号

shouldCompact() 同时接收 token 占用和内存压力快照。 后者在云端阶段是 undefined，接入本地模型后才生效—— 接口从第一天就留好，不是事后补。

子 agent 要准入

spawn_subagent 就是一个普通工具，只是带了 requiresAdmission 标志。资源不够时返回明确原因和建议等待时长， 让模型自己决定是等还是改成串行。

摘要策略可插拔

Summarizer 是接口，第一个实现是纯规则裁剪、完全不调模型—— 本地模型写摘要慢、占 GPU、还会幻觉。哪种更好用真实任务完成率来比，不靠感觉。

现在是什么状态

这是一个公开构建中的项目。下面是此刻的真实情况，不是路线图的措辞包装。

已经有了

  • 三层架构与单向依赖约束，由 dependency-cruiser 在 CI 强制
  • 覆盖模型调用、工具、压缩、沙箱、资源探测、可观测性的完整类型契约
  • 模型调用适配器、可脚本化测试 provider，以及带四关门禁的工具执行层
  • 可流式重组工具参数、执行工具并继续推理的 ReAct agent loop
  • BPE token 计账、安全边界压缩，以及可恢复的 append-only JSONL 会话
  • 每个里程碑的验收命令与桩替换清单

还没有

  • 可复用的 AgentSession、真实权限策略与系统沙箱
  • 任何评测数据
  • 可安装的发行版本
